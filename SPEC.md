# ezhttp specification

This is the list of behaviors ezhttp guarantees, each under a stable requirement ID. Every requirement has one of two levels. A **Proved** requirement holds for every input, and is backed by a quantified law (a `for` or `exs` binder) in LAWS.bend that passes the proof gate. A **Trusted** requirement is an assumption ezhttp cannot check from inside its own gate, and it is listed in the trust boundary below. A Proved requirement whose law has not landed yet has status **pending**: we intend to prove it, and until then it is not guaranteed. The proof gate is this check: the first line `bend PROOF.bend` prints is exactly `ALL PROOFS CHECK`. Tests and fixtures are never evidence for a requirement.

This file starts with the server, percent-encoding, the client's requests, timeout and redirects, multipart form bodies, and HTML escaping. ezhttp's other laws (URL parsing, message framing, credentials, cookies, caching, CORS) are not inventoried here yet, so this file promises nothing about them.

## Format

A requirement table is any table whose header row is exactly `| ID | Requirement | Level | Status | Law |`. An ID is uppercase segments joined by hyphens, at least two (`[A-Z][A-Z0-9]*(-[A-Z0-9]+)+`), unique within the requirement tables, and never reused once released. Level is `Proved` or `Trusted`. Status is `proved` or `pending` for a Proved row and empty for a Trusted row. A Law cell holds `<path> <law>` entries, paths relative to this file, separated by `; `. A Trusted row names none.

A law proves a requirement when a comment line `# <ID>`, alone on its line, sits in the unbroken comment block directly above its `law` line. A law may carry several tags, one per line.

### Client requests and timeout (HTTP-CLI)

`src/wirespec.bend` decides what the client sends and when it has heard a whole answer, and does no IO. `wire.exchange` turns a method, a parsed URL, headers and a body into the scheme, host, port, method and request text the wire effect is handed, and `src/http.bend` decides the request's header fields; `src/client.bend` and `src/wire.bend` send it and read the answer as it decides (HTTP-TRUST-5).

`http.get_opts`, `http.request_opts`, `http.post_opts`, `http.put_opts` and `http.delete_opts` take a timeout in milliseconds. It travels to the wire effect in the spec `src/wirespec.bend` writes, where the scheme line may carry it after a space as 32 binary digits, least significant first; the effect honours it (HTTP-TRUST-3). What a failed exchange is reported as is decided in `src/wirespec.bend` too.

### Redirects (HTTP-REDIR)

`http.get_opts` with `follow` set follows redirects, and so does `http.request_opts` when the method is GET. GET is the only method that follows them (a POST, PUT or DELETE answers a redirect as its response; 303-to-GET is not done), so every hop is a GET with the caller's headers and timeout; the first carries the caller's body and the hops after it none. A chain is at most 10 hops (httpx allows 20); a chain that runs out answers its last response, a redirect. A Location is resolved against the current URL as RFC 3986 §5.2 resolves a reference against a base URI. The decisions live in `src/redirect.bend`, which does no IO; `client.follow` in `src/client.bend` acts on them (HTTP-TRUST-4).

## Trust boundary

| ID | Assumption | Why it is trusted |
| :---- | :---- | :---- |
| HTTP-TRUST-1 | Base's TCP effects report a failed accept, recv or send as `Fail` and never end the process themselves. | They are foreign C in Bend's runtime (`effs/tcp_*.c`), which no law reaches. |
| HTTP-TRUST-2 | `src/server.bend` acts on `src/step.bend`'s answers in order, as the requirement states. | It is IO sequencing: Base's effects are foreign, so the checker cannot run an IO program and no law can state what happens after an effect. Every decision it acts on is HTTP-SRV-1 to 4. `http.serve_forever` is also `@unsafe` recursion, outside the termination check. |
| HTTP-TRUST-3 | The wire effect honours the timeout the spec carries and reports running out of time as status 28, sends the tail's octets as bytes after the request text, and its reads answer what arrived, as the requirement states. | It is foreign C and JS (`src/effs/wire.c`, `wire.js`) over sockets and OpenSSL, which no law reaches. What the timeout is (HTTP-CLI-1), what status 28 is reported as (HTTP-CLI-3), and when the answer is complete (HTTP-CLI-5, 6) are proved; the effect decides none of them. |
| HTTP-TRUST-5 | `src/client.bend` and `src/wire.bend` act on `src/wirespec.bend`'s answers in order, as the requirement states. | It is IO sequencing over the wire effect, which no law can state. Every decision it acts on is HTTP-CLI-4 to 10. |
| HTTP-TRUST-4 | `client.follow` acts on `src/redirect.bend`'s hops in order, as the requirement states. | It is IO sequencing over the wire effect, which no law can state. Every decision it acts on is HTTP-REDIR-1 to 6. |

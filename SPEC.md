# ezhttp specification

This is the list of behaviors ezhttp guarantees, each under a stable requirement ID. Every requirement has one of two levels. A **Proved** requirement holds for every input, and is backed by a quantified law (a `for` or `exs` binder) in LAWS.bend that passes the proof gate. A **Trusted** requirement is an assumption ezhttp cannot check from inside its own gate, and it is listed in the trust boundary below. A Proved requirement whose law has not landed yet has status **pending**: we intend to prove it, and until then it is not guaranteed. The proof gate is this check: the first line `bend PROOF.bend` prints is exactly `ALL PROOFS CHECK`. Tests and fixtures are never evidence for a requirement.

This file starts with the server, percent-encoding, the client's requests, timeout and redirects, multipart form bodies, HTML escaping, percent-decoding and query strings, HTML character references, and the Cookie header sent back after Set-Cookie. ezhttp's other laws (URL parsing, message framing, credentials, the cookie jar in `src/cookie.bend`, caching, CORS) are not inventoried here yet, so this file promises nothing about them.

## Format

A requirement table is any table whose header row is exactly `| ID | Requirement | Level | Status | Law |`. An ID is uppercase segments joined by hyphens, at least two (`[A-Z][A-Z0-9]*(-[A-Z0-9]+)+`), unique within the requirement tables, and never reused once released. Level is `Proved` or `Trusted`. Status is `proved` or `pending` for a Proved row and empty for a Trusted row. A Law cell holds `<path> <law>` entries, paths relative to this file, separated by `; `. A Trusted row names none.

A law proves a requirement when a comment line `# <ID>`, alone on its line, sits in the unbroken comment block directly above its `law` line. A law may carry several tags, one per line.

## Requirements

### Server (HTTP-SRV)

The server's decisions live in `src/step.bend` and `src/http.bend`, which do no IO; `src/server.bend` runs the effects and acts on them (HTTP-TRUST-2). Each connection is served on its own fork, so connections overlap. `http.serve_with`, `http.serve_io_with` and `http.serve_forever_with` hand the handler a context value with each request (`Server.Req`: the request as text and its body's octets) and take a reply as text, as packed octets, or streamed from a channel of octet chunks; `http.serve`, `http.serve_io`, `http.serve_once` and `http.serve_forever` are those with a text handler and no context. It receives a request as octets, one character each (HTTP-BODY-1), so its Content-Length counts octets.

### Percent-encoding (HTTP-URL)

`quote_path(s)` and `quote_component(s)` (`src/pct.bend`) percent-encode a string as RFC 3986 §2.1 describes, the way Python's `urllib.parse.quote(s)` and `urllib.parse.quote(s, safe="")` do. A character is a Unicode scalar value (U+0000 to U+10FFFF, no surrogates). Its UTF-8 encoding is the one RFC 3629 §3 tabulates.

### Client requests and timeout (HTTP-CLI)

`src/wirespec.bend` decides what the client sends, when it has heard a whole answer, and what a failed exchange is reported as, and does no IO. It judges the answer read by read: the state it carries from one read to the next (`Http.hear`, in `src/http.bend`) is advanced by each read's text alone, and is proved to decide exactly what judging all the text received would (HTTP-CLI-12). `wire.exchange` turns a method, a parsed URL, headers and a body into the scheme, host, port, method and request text that is sent, and `src/http.bend` decides the request's header fields; `src/client.bend` and `src/wire.bend` send it over bend-kit-wire's sockets and read the answer as it decides (HTTP-TRUST-3, HTTP-TRUST-5). The answer is received as octets, one character each (HTTP-BODY-1).

An exchange's answer is the response's octets, packed, or the reason the exchange failed: a non-zero status on its first line, then the reason (HTTP-CLI-13). The client judges each receive by its count of octets when that decides it, and by its text otherwise (HTTP-CLI-6), plans the response from its head with `src/http.bend`'s decisions (HTTP-CLI-15), and copies the body out of the packed octets without turning it into text (HTTP-TRUST-9). `http.get_opts`, `http.request_opts`, `http.post_opts`, `http.put_opts` and `http.delete_opts` take a timeout in milliseconds, which becomes the deadline of every socket call the exchange makes (HTTP-CLI-1, 2).

### Bodies as octets (HTTP-BODY)

What the client and the server receive is octets. The server turns each receive into text, one character per octet, by `Bytes.to_string` (HTTP-TRUST-3); the client keeps a response's octets packed, and turns into text only a receive it must judge by its text (HTTP-CLI-6), its heads and its chunk-size lines (HTTP-TRUST-9). The octet walks in `src/http.bend` (`octs.len`, `octs.take`, `octs.drop`, and those built on them) count one octet per character, so every Content-Length and chunk size counts octets (RFC 9110 §8.6, RFC 9112 §6.3, §7.1). Text is decoded from octets only at the end, for the caller (`Qs.octets.text`, `step.text`), and a response body only when the caller asks (`body_text`). A text written onto the wire (a request's or a reply's text body) is still counted as its UTF-8 octets (`utf8.len`).

### Redirects (HTTP-REDIR)

`http.get_opts` with `follow` set follows redirects, and so does `http.request_opts` when the method is GET. GET is the only method that follows them (a POST, PUT or DELETE answers a redirect as its response; 303-to-GET is not done), so every hop is a GET with the caller's headers and timeout; the first carries the caller's body and the hops after it none. ## Trust boundary

| ID | Assumption | Why it is trusted |
| :---- | :---- | :---- |
| HTTP-TRUST-1 | Base's TCP effects and bend-kit-wire's `recv` report a failure as `Fail`, never end the process themselves, and receive octets as the requirement states. | They are foreign C in Bend's runtime (`effs/tcp_*.c`) and in bend-kit-wire (`effs/wire.c`), which no law reaches. |
| HTTP-TRUST-2 | `src/server.bend` acts on `src/step.bend`'s answers in order, forking each connection, as the requirement states. | It is IO sequencing over Base's and bend-kit-wire's effects and the runtime's `IO.spawn` and channels: the checker cannot run an IO program and no law can state what happens after an effect, or which fork runs when. Every decision it acts on is HTTP-SRV-1 to 9. `http.serve_forever` and `http.serve_forever_with` are also `@unsafe` recursion, outside the termination check. |
| HTTP-TRUST-3 | bend-kit-wire, bend-kit-dns and bend-kit-bytes connect, resolve, send, receive and pack octets as the requirement states. | They are another project's code (github.com/paymog/bend-kit, Apache-2.0), pinned by hash in ez.toml and upgraded deliberately: foreign C and JS (`effs/wire.c`, `wire.js`, `effs/dns.c`, `dns.js`) over sockets, getaddrinfo and OpenSSL, and Bend over packed `Array<U32>` words that no law here reaches. bend-kit-wire ships no LAWS file, so nothing proves its comments. What the deadline is (HTTP-CLI-1, 2), what is sent (HTTP-CLI-10), what a failure is reported as (HTTP-CLI-13, 14) and when the answer is complete (HTTP-CLI-5, 6) are proved; bend-kit decides none of them. |
